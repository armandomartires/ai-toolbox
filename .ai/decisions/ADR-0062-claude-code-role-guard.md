# ADR-0062 — A role guard admits the seven refused terms to Claude Code

**Status**: accepted 2026-11-12. Written by an agent and proposed 2026-11-11. The human parked the task after the fourth risk review, then said "Complete 0271" on 2026-11-12; the fourth review's findings are closed below, and a fifth review ran before it landed.
**Date**: 2026-11-11
**Task**: `TASK-0271`

Proposed under the alignment plan's P1.1 with the human's decisions D1=B (measure each term first, supersede ADR-0018 clause 8.3 only for the terms that pass) and Q10=A (the guard asks for two weeks, then denies). Scope: Claude Code emission of the seven terms below and the roles that carry them. OpenCode is unchanged.

## Context

ADR-0018 clause 8 makes the emitter refuse a term a client cannot enforce, and clause 8.3 records the consequence: a role whose profile cannot be enforced on Claude Code is OpenCode-only. Seven terms had no per-agent Claude Code expression, because `tools` and `disallowedTools` gate whole tools and have no `ask` state: `test-files-only`, `bash-allowlist`, `test-allowlist`, `no-force-push`, `no-bypass`, `push-requires-confirmation`, `webfetch-requires-confirmation`. So 11 of the 15 roles never reached Claude Code. Clause 8.4 rejected the two workarounds "for now" (a session-wide `permissions.deny` rule, and a `PreToolUse` hook) and allowed a later ADR to revisit either "with a worked example". This ADR is that worked example for the hook only.

## Measurement (2026-11-11, reproducible on the host)

No live session was started: the measurement uses only what the host runs without spending credentials.

**The engine's contract.** The declarations Claude Code 2.1.321 writes beside a mod (`mods/<mod>/claude/.claude-plugin/types/claude-code/index.d.ts`, untracked, written by the engine; the CLI on PATH is 2.1.318):

- `BaseHookInput.agent_type`: "Present when the hook fires from within a subagent (alongside agent_id), or on the main thread of a session started with --agent (without agent_id)". So one hook can tell a role's calls from everyone else's, for subagent roles and for `primary` roles run with `--agent`.
- `PreToolUseDecision`: `allow`, `ask` ("Asks the user before the call runs"), `deny` ("Refuses the call; the model receives the text as the reason"), or none, "which passes the call on to the normal permission flow". So the third state clause 8 missed exists at the hook layer.
- `AgentSpec.name`: a plugin's agent type is `<plugin>:<name>`. The guard acts **only** on `ai-toolbox-agents:<role>`. A bare `<role>`, or another plugin's agent of the same name, gets no decision.
- The tool declarations (`claude-code-tools/index.d.ts`) list `PowerShell` and `Monitor`, each taking a shell `command`. A role whose shell is shaped must lose those too (see Findings).
- No `onFailure` field exists in these declarations. The brief's `onFailure: block` is carried out by the guard and its launcher instead (Decision 2).

So a command hook cannot be run under it.

## Decision

1. **Supersedes ADR-0018 clause 8.3 for the seven terms above, on Claude Code only.** A role declaring them is no longer OpenCode-only on that ground. Clause 8.3's named disposition of `git-ops` is withdrawn; `shell-runner`, also named there, has never been authored and is untouched. Clauses 8.1, 8.2 and 8.5 stand, and the emitter still refuses any term with no mapping. **Clause 8.4 is lifted for the `PreToolUse` hook only, and only for this hook**; its rejection of session-wide per-role permission rules stands. Its concern that the hook is a second artifact the agent file does not own is answered by generation: the guard's rules come from `agents/<role>/agent.md` through `scripts/emit-agents.py --guard-json=`. ADR-0018 carries a pointer under 8.3 and 8.4.
2. **The guard.** `configs/claude-code/hooks/role-guard.py` is a PreToolUse hook keyed on `agent_type`, matched on the shell, edit and web tools and on every tool it withholds (below). Its rules are `role-guard.json`, generated, one entry per guarded role. It never answers `allow`: an allowed call gets no decision, so the permission rules (TASK-0276's included) still apply. `bash hooks/role-guard.sh` starts it with `python3`, else `python` (3.8+), and always exits 0: with no working python, or a guard that exits non-zero, a call from `ai-toolbox-agents:<role>` is denied and every other call gets no decision. Its rules:
   - **One parse of the raw text.** A command holding a character bash and the guard could read differently (non-ASCII, NBSP, a control character other than tab and newline) is denied. The rest is lexed once (shlex, POSIX, shell operators and newline as tokens, no comments) and that one token list feeds both the deny rules and the allowlist. Wrappers (`env`, `command`, `exec`, `nice`, `timeout`, `xargs` and kin, and bash's `!`) are dropped, and a shell's `-c` string or an `eval`'s words are lexed as the command; an operator inside that string is denied. Git options are read as git reads them: short clusters expanded (`-an` is `-a -n`), a required short value skipped (`-m --` is a message, not end of options), an optional one (`-S`, `-u`, `-t`) taking the rest of its cluster and never the next word (`-Sm -n` is key id `m`, then `-n`), a long option denied when it is a named one or any abbreviation of it (gitcli(7)), a glob before the real `--` denied. A `--` straight after a long option written without `=` is that option's value, not the end of options (`--template -- -an`), and every word after any `--` is still checked as an option or refspec, so a pathspec that looks like a denied option is a false deny. The agent file's text globs still apply to the tokens.
   - **Denied for every guarded shell role, in every mode and before the switch:** what the guard does not model (`$`, backtick, backslash, so `$'..'` and `${..}`; unbalanced quotes; **every shell operator** — `;`, `&`, `|`, `<`, `>`, `(`, `)` and newline, alone or in any run such as `&&`, `;(` or `>|`, so a guarded role runs one simple command per call; brace expansion; `~`; `%` outside `--format=`/`--pretty=`; any environment assignment, `GIT_*` included; a wrapper option such as `timeout -s`, `env -u`, `sudo -u`, `exec -a`; a shell option such as `-lc`); any git option before the subcommand, `git config`, `core.*`, `-o`, `--output`, `--output-directory`, `--ext-diff`, `--exec`, `--upload-pack`, `--receive-pack`, `grep -O`. **`no-force-push`:** push `-f`, `--force`, `--force-with-lease`, `--force-if-includes`, `--mirror`, `-d`, `--delete`, `--prune`, `+`/`:` refspecs; reset `--hard`/`--merge`/`--keep`; checkout and switch `-f`/`--force`; branch `-f`/`-D`/`-M`/`-C`/`--force`; commit `--amend`; `rebase`, `filter-branch`, `restore`, `clean`, `update-ref`. **`no-bypass`:** commit `-n`, `--no-verify`, `--amend`; push `--no-verify`.
   - **An allowlisted shell, well-formed commands only.** Plain `'`/`"` quoting is read through (a quoted commit message is allowed); `@{u}`/`HEAD@{n}` are admitted for read-only git subcommands. A well-formed command with a comment, a `..` step or a non-git glob, or simply outside the allowlist, is asked in the trial and denied after. Allow patterns ending in `word*` are anchored at the word (`git status*` never admits `git statusX`); git-ops lists remotes with exactly `git remote -v`.
   - **Edits.** For every guarded role, `Edit`, `Write`, `MultiEdit` and `NotebookEdit` may never touch, case-insensitively and after Windows' trailing dots and spaces are stripped from each segment: any segment ending in `.git` (`.git/`, bare repositories), `.githooks/`, `.husky/`, `.pre-commit-config.yaml`, `lefthook.yml`/`.lefthook.yml`, the hooks directory from `git rev-parse --git-path hooks` (an absolute git from PATH, never the current directory; if that lookup fails, edits under the repository are denied), `.claude/settings*.json`, `.claude/{plugins,agents,commands,skills,hooks}/`, `.mcp.json`, `~/.claude.json`, `.claude/{rules,output-styles,workflows}/`, `CLAUDE.md`, `CLAUDE.local.md`, `.gitconfig`, `.config/git/`, the guard's own `role-guard.{json,py,sh}`, a plugin's `.claude-plugin/` and `hooks/hooks.json`, `.gitleaks*`; below the working directory an 8.3 short-name segment (`~1`) or an NTFS stream (`::$DATA`) is refused. Test-path roles match their globs relative to the working directory, never under a dot directory.
   - **Withheld tools.** `Workflow`, `CronCreate`, `CronDelete`, `SendMessage`, `EnterWorktree`, `ExitWorktree`, `TaskStop`, `RemoteTrigger`, `SendFile`, `ScheduleWakeup`, `Skill`, `SendToProject`, `PublishPlugin`, `Artifact`, `AppifactRepl`, `request_computer` are in each guarded agent file's `disallowedTools` and denied by the guard, with every `mcp__*` tool. WebFetch and WebSearch are asked for `webfetch-requires-confirmation`. The input is read as UTF-8; an unreadable input, a missing `role-guard.json` or an exception is a deny for a guarded agent.
3. **Ask for two weeks, then deny (Q10=A).** Until **2026-11-25** a call outside a role's allowlist is asked. From **2026-11-26, 00:00 UTC** (the guard compares the UTC date; `deny_from` in `role-guard.json`, whose one owner is `GUARD_DENY_FROM` in `scripts/emit-agents.py`) it is denied. An `ask` becomes `deny` in any permission mode where no person answers prompts: any mode other than `default`, `acceptEdits` or `plan`. An input with no `permission_mode` key is treated as `default` and keeps the `ask`. False positives during the trial are recorded in the task and fixed in the allowlists before the switch. Accepted on 2026-11-12, so the date moved one day to keep the two weeks; the human may move it again (one constant, then `scripts/build-plugin.py`).
4. **Only the ai-toolbox-agents plugin carries guarded roles.** A plugin subagent ignores a `hooks` key in its own file, so the guard is a plugin-level `hooks/hooks.json`. `scripts/build-plugin.py` emits with `--with-guard` and copies the guard, its launcher and its rules in. A plain emission (`scripts/install.sh` into `~/.claude/agents`) skips a guarded role and prunes a stale copy. This keeps this repo's tooling from shipping a guarded role without its hook; it does not make the hook run (see the fail-open paths below).
5. **Hard push rules stay in permission rules.** TASK-0276 owns `deny Bash(git push --force*)` and `ask Bash(git push*)`; the fixtures assert them without copying them. Because the plugin cannot ship permission rules, the guard denies the forms in Decision 2 itself; OpenCode's map is unchanged.
6. **Roles now emitted for Claude Code**, all through the plugin: closer, gate-runner, git-ops, implementer, park-steward, preflight, qa-test, refuter, review, run-scribe, beside the four already there. That makes 14 of 15. `designer-manager` stays OpenCode-only. It declares none of the seven terms; it was narrowed only because its delegate `git-ops` was OpenCode-only. Widening it is a separate decision.

## Findings made on the way

- **`no-bash` leaked a shell on Windows.** It withheld `Bash` only, while `PowerShell` and `Monitor` run commands too. The emitter now withholds all three for `no-bash` (adjudicator, task-planner) and for every guarded shell role, and the guard denies them. **OpenCode's `no-force-push` misses a trailing `--force`**, clusters and abbreviations; this ADR does not change OpenCode, and the gap is recorded for a later task.
- **Three risk reviews' bypasses, each a fixture run red against the earlier guard and then green:** separators, comments, aliases (`git statusX`); `git -c`, `--exec-path`, `--output`, `--ext-diff`, `git config`, `core.*`; `-n`, `--no-verif`, `--amen`; quoting, escapes, NBSP and control characters (`'-n'`, `--n"o-verify"`, `-{n,q}`, `$'\x2dn'`, `-m<NBSP> -an`); a consumed `--` (`-m -- ?n`); clusters (`-an`, `-qfu`); wrapped pushes and wrapper options; `GIT_*` assignments; subshells; `git remote -v add`; the control paths, indirect hook files and Windows aliases above; H4/M-D tools; H6, a missing or crashing python, which under `python3 … || exit 2` blocked every matched call in every session and now blocks only guarded agents; L6, `.github/` and `tests/../../x.sh`, quoted too. **The fourth review's (R-0271d) bypasses, each a fixture run red against the parked guard (38 of its checks fail) and then green:** HIGH-1, a run of operator characters lexed as one token (`git status;(git push -f)>|y`, `git log >| out`) was read as a word, so an allow pattern matched past it; every operator token is now a deny. HIGH-2, an optional-value short option (`git commit -Sm -n`) was read as a required one, so the guard skipped the `-n` git acts on; the optional ones now end the cluster. MEDIUM, `~/.claude.json` (user MCP servers) and the `.claude/` rules, output styles and workflows a session loads were editable; they are protected. Turning separators and redirection from an `ask` into a `deny` is the fix the park record proposed, and it costs nothing an allowlist admitted: every guarded shell role has an allowlist, and none of its patterns holds an operator.
- **The fifth review's (R-0271e) bypasses, each confirmed with git 2.53 in a throwaway repository, run red against the guard before the fix (24 checks) and then green:** HIGH, git takes `--` as the value of a long option that wants the next word, then reads on as options, so `git commit -m x --template -- -an` committed without running the pre-commit hook, and `git log --decorate-refs -- --output=.git/hooks/pre-commit …` wrote a hook that the next commit ran; the guard had taken every `--` as the end of options. MEDIUM, the guard's own rules and a plugin's manifest and hooks were editable. LOW, `!` and `eval` hid a forced push from the deny rules (asked, not denied). **Known and not closed: a role that writes code writes code something else runs.** The implementer and qa-test may edit scripts that a hook outside the guard later runs, such as this repository's `stop-fast-check.sh` (the main session's Stop hook) or `tests/validate.sh` (the pre-commit gate). A path list cannot tell such a script from ordinary code. The review of the diff before a commit is the control, as it is for OpenCode.
- **H2, narrowed but not closed: gate-runner's `*run-gate.sh*`.** An exact path cannot be generated: the entry point is a per-binding slot (`gate_entry_point: <FILL: …>`), and the agent file keeps one pattern on the human's decision of 2026-09-24. The guard reads it as "the executable is a file named `run-gate.sh`, run directly or as `bash`/`sh`'s first argument"; `python x.py run-gate.sh`, `sh -c …`, `env X=1 run-gate.sh`, `bash --rcfile x run-gate.sh`, `run-gate.sh.evil` are outside it. **Still open:** any reachable file of that name runs, including one another role wrote.
- **Defence in depth, not a sandbox.** The guard sits over the tools withheld in each agent file and the session's permission rules. It denies what it cannot model rather than guessing, but its lexer is not bash: a determined author of shell input may still find a parse difference it does not know, and each one found becomes a fixture.

## Not measured, and named so it is not assumed

- That a live session delivers `agent_type` to a **plugin** hook for a **plugin** subagent's call (declared, not run: no credentials), or what a hook `ask` does under `auto` or `bypassPermissions` (the guard denies there instead).
- **Fail-open paths.** The guard is not in force, and a guarded role's call proceeds under the normal permission flow, when: the hook command cannot start (no `bash` on PATH; the engine treats a hook error other than exit 2 as non-blocking); the hook times out (`"timeout": 30`; behaviour unverified, L4); `disableAllHooks` is set, or `allowManagedHooksOnly` excludes plugin hooks; the plugin is disabled or the role is loaded from another copy; the caller is an agent-team teammate, whose `agent_type` is its given name (H5, a fixture records the gap).
- **Git's option semantics** come from gitcli(7) and `git <sub> -h` of git 2.53 (required short values), not from running each bypass through git: the worktree's isolation refuses git outside it. The rules over-match on purpose (any abbreviation of a denied long option is denied); a short option git takes a value for but the guard does not list is read as options, a false deny, never a bypass.
- Bash matching is word-based; a test command such as `pytest` still runs code that can write anywhere, as in OpenCode.

## Alternatives considered

- **Keep the seven refused (status quo)**, rejected by D1=B once the fixtures passed; **deny from day one**, ruled out by Q10=A.
- **Frontmatter `hooks` in each agent file.** Plugin subagents ignore it, and the path to the guard is unknown at emission time.
- **Session-wide permission rules per role.** This is clause 8.4's first workaround, and it leaks one role's boundary into every agent. It was not reopened.
- **A `tools` allowlist per guarded role (H4, M-D).** Not done yet: it would withhold new engine tools by default, but each role's needed tools must first be declared in `agents/<role>/agent.md`; until then a new engine tool reaches a guarded role unless added to the withheld list.

## Consequences

- 14 of 15 roles reach Claude Code with their boundaries enforced by a generated, fixture-tested guard wherever the plugin's hook runs; the fail-open paths above are the exceptions.
- The plugin now ships one hook, needs `bash` and `python3` (or `python`) 3.8+, and a missing python costs only the guarded agents. `tests/test-install.sh` P7b asserts the agents plugin's hooks are the guard and its launcher alone. Rollback: revert the task commit. The roles become OpenCode-only again and the plugin goes back to 4 agents.
