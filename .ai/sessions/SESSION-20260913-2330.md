- **Three defects found, two in code written this same session.** All three
  came from fails-when-broken proofs; none would have surfaced on the happy
  path:
  1. `chmod +x` never reached git's index — `core.filemode=false` here, so
     the hook staged as `100644`, and git silently ignores a
     non-executable hook. The gate would have been **dead on arrival** for
     anyone cloning onto a filesystem that honours the bit, while working
     fine locally. Fixed with `git update-index --chmod=+x`.
  2. My first `validate.sh` hook check was **unfalsifiable**: guarded with
     `[ -d .githooks ]` for leniency, which meant deleting the hook made
     the check pass. Now unconditional.
  3. That check also tested the wrong property — `[ -x ]` can never fail on
     a mount that reports `rwxrwxrwx` and ignores `chmod -x`. It now
     inspects the mode **git records**, which is both testable and the
     thing that actually disables a hook.
  Connecting pattern: **the environment lied about the property being
  checked.** The filesystem reports permissions it does not enforce; git
  records permissions the filesystem does not reflect. Checking the
  convenient property instead of the authoritative one produced checks
  that passed for the wrong reasons.
- **The first hook proof was itself broken**, and it is recorded rather
  than quietly fixed: it opened with `git stash -u`, which stashed the
  then-untracked hook and silently disarmed every case — the commit that
  should have been refused went through, reading as a hook failure when it
  was a test failure. Rewritten to require a clean tree and run after the
  hook was committed. Second time this project has been saved by
  distrusting a result: REVIEW-0004 recorded that a *green* result is not
  evidence; here a *red* one was equally untrustworthy.
- De-duplication proven two independent ways, because a checksum alone
