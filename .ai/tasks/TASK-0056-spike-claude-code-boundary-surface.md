# TASK-0056 — Spike: what can Claude Code enforce per agent, and is a dead delegate silent?

## Objective

Settle **F5** — whether an emitted Claude Code role whose `tools: Agent(x)`
names a role that is never emitted for Claude Code is a *silent* dead reference
— and establish whether **any** command boundary is expressible per agent in
Claude Code at all. **Findings, not components.**

## Minimal context

F5 is not hypothetical. `agents/designer-manager/agent.md` declares
`clients: [claude-code, opencode]` and `delegates_to: git-ops`, while
`agents/git-ops/agent.md` declares `clients: [opencode]` only. So the emitted
`~/.claude/agents/designer-manager.md` names a delegate that
`~/.claude/agents/` does not contain — **today, on this machine.**

If that is silent, this repo has a live defect of exactly the class `ADR-0018`
clause 8 exists to prevent: a file that loads, runs, looks correct, and does
less than it says. It would also justify the new `validate.sh` check in
`TASK-0059`, which otherwise would be a rule invented without evidence.

The second question exists because `PLAN-0006` asserts that seven of nine roles
are OpenCode-only. That assertion rests on the authoring guide's table, which
rests on `TASK-0036`. Before nine roles are authored on it, one direct check is
cheap: `ADR-0018`'s own closing instruction is to re-verify rather than cite,
and the installed Claude Code was, at that time, *"older than six of the patch
versions its own documentation cites."*

## Scope

### Included

- **F5**: does Claude Code warn, error, or stay silent when a subagent
  definition's `tools: Agent(...)` names a non-existent agent? Test against the
  live `designer-manager` emission, and against a scratch fixture naming an
  obviously absent role.
- Whether a per-agent command boundary — "git commands only", "no `git push`" —
  is expressible at all, and whether `disallowedTools` with a specifier such as
  `Bash(git push *)` removes the matching commands or the whole `Bash` tool.
  The authoring guide says the latter; confirm it still holds.
- Whether `isolation: worktree` is settable per agent, and what it confines.
  This is `ADR-0018` clause 7's open question, assigned to `TASK-0040` and still
  unresolved, and **all nine new roles declare `worktree-only`**.
- A negative control for each claim, proved able to fail first.

### Not included

- Fixing `designer-manager` if F5 confirms the defect. Record it, raise it,
  leave it. A fix belongs in its own task with its own acceptance criteria.
- The Workflow runtime — its behaviour is documented and `TASK-0066`'s concern.
- OpenCode — that is `TASK-0055`.

## Risks and rollback

- **Fixing what this task is only meant to observe.** `designer-manager` is a
  live role in a shipped loop; changing it here would put a fix outside any task
  that planned for it.
- **Reading an absence as a confirmation.** If nothing is printed, that is
  evidence only if a control shows something *would* have been printed.
- **Stale emitted files.** Nothing verifies their freshness by design; if they
  look wrong, re-run `install.sh` rather than concluding from them.
- Rollback: delete the scratch fixtures.
