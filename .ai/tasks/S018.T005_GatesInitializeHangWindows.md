Find why the gates MCP server gives no answer to `initialize` within 120 s on Windows, under `tests/smoke-mcp.sh` and a direct stdio client (`S011.T027_GatesHttpTransport.md`, line 87), while `scripts/mcp-tool-lock.py` (`uv run --frozen --no-dev`, minimal env, UTF-8, `stdin=PIPE`) succeeded (`S011.T011`). ## Verification

- Hypothesis 1 (`uv run` re-syncing): ruled out. `uv --directory mcp-servers/gates lock --check --offline` → `Resolved 53 packages in 13ms`; a frozen sync from cache took 7.16 s.
- Hypothesis 2 (Python 3.14): ruled out. `uv ... run --frozen python -V` → `Python 3.11.15`.
- Hypotheses 3 and 4 (text pipes, full environment): ruled out. The server answered `initialize` in 1.6–1.8 s under the harness's exact launch.
- Cause, one factor varied: with `proc.terminate()` the reply came after 1.6 s, then `stderr.read()` blocked with no EOF after 20 s and two server processes stayed alive; with `taskkill /T /F` the read returned at once and none stayed. On Windows `terminate()` kills only `uv.exe`; the venv launcher and interpreter keep stderr open.
- Unchanged harness: hung over 180 s and printed `PASS gates` only once the orphans were killed (3m26s).
- Fixed harness: `bash tests/smoke-mcp.sh --server gates` → `PASS gates: serverInfo.name=gates version=1.30.0 …`, `1 passed, 0 failed, 0 skipped`, exit 0 in 5 s; `GATES_TRANSPORT=bogus … --timeout 20` → `FAIL gates: no stdout (exit 2) …`, exit 1 in 5 s; `--timeout 0` → `FAIL … did not answer initialize`, exit 1 in 3 s; 0 leftover gates or uv processes after each.
- Independent review: pass, no blocking finding; its first three advisories (a bounded taskkill, shutdown in try/finally, readers joined before their pipes close) applied.
- Not run: Linux and the network-bound servers' smoke runs.
- `tests/validate.sh` → run by the pre-commit hook on this commit.
