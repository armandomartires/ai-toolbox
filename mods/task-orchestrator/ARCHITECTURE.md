# task-orchestrator: enforcement and advice

Every claim this mod makes falls in one of three columns. The first is what the engine refuses on the mod's word; the second is what the mod sees after the fact; the third is text the model is asked to follow.

## Enforced in code

| Rule | Where |
|---|---|
| At most `limits.maxConcurrent` workers run; the next waits in the ledger and starts when one ends | `ledger.startBlocker`, `runnable`; `register.tsx` `tick` |
| A worker never delegates: a spawn whose parent is a ledger worker is denied; a worker's call to `Agent`, `Workflow`, `SendMessage`, `TaskStop`, `EnterWorktree` or `ExitWorktree` is denied, whether orchestration is on or off; the profiles also list them under `disallowedTools` | `agent.spawn` hook, `tool.call` hook, `ensureProfile` |
| One non-isolated writer at a time; isolated writers (own worktree) may run beside each other only with disjoint allowed files | `startBlocker` |
| A worker writes (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`) only inside its allowed files, never a file another running writer owns; a read-only role never writes and never runs `Bash`. The target is resolved first (`..` and `.` collapsed, backslashes turned to `/`, a root that starts with a drive letter compared without case) and confined to the worker's checkout, so an absolute path outside it is refused, and every write is refused when the checkout path is empty or relative (`<id>: the checkout path is unknown, so the write is refused`). The resolver does not follow symlinks or junctions, does not expand 8.3 short names, does not strip trailing dots or spaces, and folds case only for a drive-letter root; an allowed entry matches whole path segments, and an empty list means the whole checkout | `normalizePath`, `resolveIn`, `covers`, `writeBlocker`, `tool.call` hook; read-only profiles carry `tools: [Read, Grep, Glob, LS]` |
| A model is ranked and gated by its family, not its string: `familyOf` and `familyRank` place `claude-fable-5-1` with `fable`, `fallback` climbs the ladder by rank, and a model with no known family passes `route` unchanged when it is available; it is refused when it is unavailable (there is no rung to fall back from), when escalated, or for a session. `xhigh`, `max` and `fable` are refused without the opt-in; an effort outside the five levels is never sent | `familyOf`, `familyRank`, `router.gate`, `router.fallback`, `router.route` |
| A `dispatch` under the id of a `blocked`, `failed` or `partial` task is that task's next retry, in its place; retries are counted per task and refused past the limit, as escalations are; a `completed`, `cancelled`, queued or running id is refused | `retryTask`, `mayRetry`, `mayEscalate`, `escalationOf` (a retry on a bigger model or higher effort counts as an escalation) |
| A dependant starts only once every dependency completed. Behind one that ended without completing it stays queued, so a retry of that one can still start it, and `status` and `collect` name what it waits on; `collect` does not wait it out | `startBlocker`, `stalledBy` |
| A spawn auto mode gives no verdict is issued once more, unchanged; refused again, its task is blocked with `handoff`, and the no-verdict is remembered for the session, so every later start hands off at once without two refused spawns | `register.tsx` `start`, `noVerdictSeen` |
| A hand-off of either kind (subagent or session) holds its slot against the cap and, as a non-isolated writer, the one-writer rule; it is `running` to `overall`, not `blocked`; its dependants are reported as waiting for the coordinator's call, never told to re-dispatch it | `holdsSlot`, `activeWriters`, `overall`, `stalledBy`, `handoffRoot` |
| Every ledger write runs over the rows as they are when it lands, inside the atom's updater: `dispatch` adds its row there (a dispatch beside it, or a worker's end during its awaits, is not written over); `queued → running` is a compare-and-set, so two ticks start a task once and a cancel in between holds; the settles that follow a spawn, an end, a session read, a cancel and an adoption apply only while the row still has the status they expect; ticks run one after the other | `settle(when)`, `answerDispatch`, `start`, `tick` |
| `cancel` of a row claimed by a tick whose spawn is in flight (no agent id yet) answers `still starting` and changes nothing; a `TaskStop` answered with `isError` is a refusal; after a cancel the next queued task starts in the same answer | `cancelTask`, `answerCancel` |
| The hidden note and the toast carry the task's id, role and status only; a worker's `Next:` is one line of at most 200 characters with a leading `[task-orchestrator]` stripped; a dependency's findings enter the next assignment under a line naming them as quoted data, indented, at most 1500 characters | `ended`, `plain`, `parseReport`, `quotedFindings` |
| The project's `.claude/task-orchestrator.json` cannot widen: its `optIn` is refused, a limit above the one in force is refused (the known limits are read as own keys, so a `__proto__` key cannot smuggle one), its `providers` is refused like `optIn`, its `policy` and `routes` apply to the session only, and nothing from it is persisted; the store entry per project, keyed by the checkout's path, or `(no cwd)`, carries `v: 2` and holds `enabled` plus the `/orchestrate` choices only (`chosen`), not the home file's values; `loadConfig` reads an older entry as `enabled` alone and `status` lists it under `config refused` | `projectOverride`, `loadConfig`, `saveSettings`, `settingsKey`, `chosen` |
| A session whose first prompt starts with `# Assignment ` gets no coordinator protocol and is turned off in memory: a worker session never becomes a coordinator | `prompt.submit` hook |
| A worker runs under its role's profile only at the table's settings; any other model, effort or isolation registers and spawns a profile of its own (`<role>--<model>-<effort>[-wt]`), so concurrent tasks of one role never share a registration | `profileName`, `ensureProfile`, `start` |
| A hand-off is adopted only from an Agent call of the task's role's own profile (the hand-off's: always registered, the effort on the call) or its exact profile, whose prompt's header, `# Assignment <id> — role`, names the task (else its `name`; the desktop's Agent tool takes none), and only when the task could start now (concurrency, writers); nothing of the call is rewritten | `agent.spawn` hook |
| A `runAs: "session"` task is never spawned by the mod: `start` hands it off, and its dispatch answers with the `start_session` call to make (`initiation` user_asked, `context` fresh, name the task id, model, effort, `use_worktree` true, `wake_when_done` true, an 80-plus-character `background`, the assignment as `prompt`) | `start` (session branch), `sessionCall`, `handoffText` |
| A session dispatch above the coordinator's model family or effort is refused, since the app would start it lower in silence. The coordinator's effort is that of its latest model request, seeded at session start from its settings (`settingsEffort`); the effort check is skipped only when neither gives a level | `sessionGate`, `coordinatorEffort` (set by `turn.step`) |
| A session task is handed off only by a call made inside a turn the person started: `personTurn` is set by a prompt whose origin is absent, `composer` or `bridge` (an `sdk` prompt is code's, not the person's) and cleared when the coordinator's own turn ends, so it is never stale. A worker's end (`turn.complete` with an agent id) never hands off. A queued session task waits as "waiting for the person's turn", and the next person-started prompt hands it off with its lines attached as context. This is the mod's own gate, derived from the prompt's origin: whether the app refuses a `start_session` on that turn is the app's | `personTurn`, `prompt.submit`, `turn.complete`, `tick` |
| A `start_session` is adopted only into a session task that is handed off and blocked, that could start now (cap, dependencies), and only if the call carries the hand-off's model (the alias or an id of its family), its effort and `use_worktree` true, else it is denied with the difference and nothing reaches the app; a cancelled, running or queued one is denied, and any other `start_session` passes untouched. An `Agent` call naming a session task's header is denied: only `start_session` starts it. A refusal of the app's leaves the row blocked with its words; an answer with no `local_<uuid>` leaves it handed off | `adoptSession`, `callMismatch`, `sessionIdIn`, `agent.spawn` hook |
| A session task has no write fence and no one-writer rule, and is always `isolated` (its own worktree, landing by rebase, ADR-0023) | `startBlocker` (writer checks skipped), `activeWriters`, `start` |
| A running session is read through `get_session` (`isRunning`) once a pass, then `list_events` once it has ended; its last message is the report, quoted data. A list of events that cannot be parsed, or holds no message, ends the task `partial` with "no report was read" and the raw tail quoted as such, never as a report. A session that ends in `collect` runs the same end path as a subagent's `turn.complete` (toast, then the queued work starts, a session dependant being handed off only inside a person's turn). A refused or unreadable read prints the two calls for the coordinator and the task is not waited on. A task behind a session handed off is reported as waiting for its `start_session` call, not stalled, and `collect` does not wait it out | `refreshSession`, `lastMessage`, `ended`, `sessionReads`, `answerCollect`, `handoffRoot` |
| `collect` sleeps only for a session: a running session read through the app, or a task queued behind running sessions only (the named tasks' dependencies are read too). With no such task pending it answers at once: a subagent's `turn.complete` cannot reach the mod inside the coordinator's hook (see *Observed*, 2026-11-05), so its end note is what wakes the coordinator, and sleeping on it only spent the hook's budget | `isPending`, `answerCollect` (`related`) |
| `cancel` of a running session calls `stop_session`; if refused, the answer says the session keeps running and to stop it by hand | `cancelTask` |
| A worker that ends with no `Status:` line, whose transcript (`$.session.messages({ agentId })`) ends on a tool result, stopped at its turn cap. Its task ends `partial`, and its reason names the cap, its worktree (`agent-<id>` on `worktree-agent-<id>`, from `git worktree list`) or the session's checkout, the uncommitted changes and the commits past its base, and says to resume it with `SendMessage` rather than re-dispatch it. That agent's next `turn.start` sets the task back to `running`, so the fence holds its calls, and its next `turn.complete` closes the task. A worker that ended on its own `partial` report, or a `blocked` one (not a hand-off), is resumed the same way (`TASK-0289`): `admit` takes `resume`, which admits a blocked row only while it is not a hand-off | `cutOffMidStep`, `workOf`, `turnCapReason`, `isResumable`, the `turn.start` and `turn.complete` hooks |
| Every path into `running` passes one admission check, `admit`: a status compare-and-set on the row's expected status, then the cap and writer rules as for a queued row. The five paths are `start` (a dispatch or a tick), an Agent-tool spawn of a worker profile (`admitNew`, run on a provisional row before the spawn and again inside the updater after it, with the first free `agent-<n>` as id when the spawn's name is taken), an adopted subagent hand-off, an adopted `start_session` and a resume (turn-capped, or self-stopped `partial` or `blocked`); all but the spawn run it through `admitRow` in one `update`. A writer taken through the Agent tool has an empty allowed-files list, so it counts as a writer. A resume the cap or the writer rule refuses leaves the task as it was (`partial` or `blocked`) and the coordinator is told by a hidden note. A spawn refused only after `next()` has answered cannot be denied (the engine refuses a deny then), so its agent is stopped with `TaskStop` when the engine allows it (`stopWorker`, the result checked with `refusedCall`) and the coordinator told by a note; if the stop is refused, the note says so and names the agent id, and the worker runs untracked and unfenced until the coordinator stops it | `admit`, `admitNew`, `freeAgentId`, `admitRow`, `agent.spawn` hook, `turn.start` hook |
| A dependant's stall text names the way out by its root's state: a cancelled root, cancel the dependant or dispatch a new task; a root `partial` at its turn cap, resume it with `SendMessage` to its agent id; any other, retry n of the retry limit, or cancel when the retries are spent | `stallText`, `stalledBy` |
| The write fence and the nesting guard hold whether orchestration is on or off, keyed on the task's row, not on `enabled`; `/orchestrate off` keeps running workers fenced. `enabled` gates new dispatches, ticks, `adoptSession`, the hand-off adoption in `agent.spawn`, the protocol injection, the Agent-tool tracking and the tool deferral; a pending hand-off's Agent call made after `off` is passed through untracked. `cancel` with no id is refused (`cancel needs a task id or "all"`); the command's bare `cancel` still means all | `tool.call` hook, `agent.spawn` hook, `answerCancel` |
| The status line counts a hand-off as running, with the queued tasks and the policy, and refreshes on dispatch and cancel; a panel row's second line carries the blocker, `retry n/<max>`, tokens and a session task's branch | `statusSummary`, `statusLine`, `blockerFor`, `taskView` |
| A run reports `done` only when no task failed, was blocked or stayed open; a hand-off counts as open | `overall` |
| While off, the four tools are described as deferred; `collect` with no ids prints a report or a hand-off's assignment once (`delivered`, keyed by id and end time), and in full again only when named by id; a writer profile lists its tools (`WRITER_TOOLS`) | `tool.describe` hook, `answerCollect`, `handoffText`, `ensureProfile` |
| Off: `dispatch` refuses; queued tasks do not start; the ledger is kept | `answerDispatch`, `tick` |
| The run survives a forced reload: after every write of `ledger` or `unavailable` the ledger, the refused models and the assignments are mirrored into the plugin store (`task-orchestrator:run:<session id>`, one entry per session) with this session's id, when their JSON changed. Only the five report fields are capped, each at 2000 characters in the mirror's copy; prompts, assignments, notes and reasons are not. `/orchestrate reset` deletes the entry (`forget`), and nothing else does, the session's end included; `session.start` restores them only into an empty ledger and only from a run that carries this session's id, never another session's | `keep`, `restore`, `forget` (`hooks/keep.ts`), `session.start` hook |
| A guard that throws fails closed: the spawn is refused, a worker's call is refused, the main loop's passes | the `.catch` handlers |

The engine's own permission checks stay in force under every worker: the mod adds denials and never an allow, never a permission mode, never a bypass. The hand-off is no exception: it moves a spawn the classifier could not judge to a call it does judge.

## Observed, not guaranteed

- **Model**: the spawn's answer carries the id core resolved the alias to (`resolvedModel`); the worker's first `turn.step` carries the model the request names (`observed`).
- **Effort**: set on the worker's registered profile (`$.agent.register` takes `effort`; `$.agent.spawn` does not), so it is **requested**. The first `turn.step` of the worker's loop carries the effort the request sends, and `status` then reports it as **observed**. Until then the line reads `effort unverified`. A model that takes no effort is reported as such.
- **A hand-off's settings**: the hand-off names the role's own profile with the model, effort and isolation on the Agent call, since a per-settings profile registered this turn was no Agent type in that turn (live, 2026-10-28). The call's effort outranks the profile's (live probe: the scout profile at low, a call at medium → observed `claude-haiku-5-5/medium`). The mod sees neither the effort nor the isolation of the call (`AgentSpawnInput` has neither): the observed line proves the effort; a worktree left off is not caught.
- **Host overrides**: `settings.model`, `modelSettings.<model>.effortLevel`, `CLAUDE_CODE_SUBAGENT_MODEL`, `CLAUDE_EFFORT`, `ANTHROPIC_MODEL` and `ANTHROPIC_SMALL_FAST_MODEL` are read at session start and listed by `status`. They are disclosed, never changed, and a `modelSettings.<model>.effortLevel` entry is worded as a disclosure, not a prediction: `dispatch` says nothing of it. Only a mismatch is warned: when a worker's observed effort (its first `turn.step` for a subagent; `get_session` for a session) differs from the requested one, its line in `status` and its notes carry `effort mismatch: requested X, observed Y`, naming the `modelSettings` effort set for that model (the observed model's id, else the alias) that likely caused it. Reason: on 2026-11-03 three workers (sonnet/medium, haiku/medium, sonnet/high) ran at their requested effort under `modelSettings.claude-sonnet-5-5.effortLevel = xhigh`, so a profile's effort outranked the host setting; the earlier dispatch note "may replace the requested effort" was a wrong prediction.
- **Resumes**: an `agent.spawn` with `resume` is passed through unchanged; a resumed worker keeps its profile. The mod registers a profile per settings and re-registers one only when its settings change; a profile registered mid-turn is taken by the Agent tool from the next turn (`$.agent.register`), which is why a hand-off line also names the effort; the observed line is what says which settings a worker actually ran under.
- **Auto mode** (Claude Code 2.1.312, desktop, 2026-10-28): every spawn the mod made with `$.agent.spawn` was refused with "The server-side auto mode classifier gave no verdict for Agent: the request that produced this action did not ask for one. Issue the action again once, as-is …", while the model's own Agent calls and a Workflow run started. The classifier judges an action against the model request that produced it, and a plugin's spawn has none: `$.agent.spawn` takes `prompt`, `description`, `subagentType`, `model`, `name` and `cwd` (`AgentSpawnArgs`), and its `tool_use_id` is the engine's, pinned, so nothing can name the coordinator's `dispatch` call or carry a consent. `$.tool.call({ tool: 'Agent' })` runs the permission check under a `tool_use_id` of its own, so it is expected to be refused the same way; not tried. What auto mode does allow is the coordinator's own Agent call, so the mod re-issues the spawn once, as the deny asks, then hands the task to that call (the role's type, the task's id as `name`, the requested model, the assignment as prompt) and adopts the spawn into the task's row. Seen live on 2026-10-28: the hand-off was printed and the coordinator's call ran, but 0.4.0 matched it by `name`, which the desktop app's Agent tool does not take, so the worker ran untracked; 0.4.1 matches the prompt's header. The deny is matched on its wording: reworded, it leaves an ordinary `blocked`, which a re-dispatch retries. `cancel` stops a worker with `$.tool.call({ tool: 'TaskStop' })`, also a plugin's call; if auto mode refuses it, `cancel` says so and the worker keeps running.
- **Session workers** (`ADR-0050`, spike 2026-11-03 with a throwaway probe mod outside this repo, in a session that offers `start_session`, one Sonnet 5.5 child at medium): the mod's `tool.call` hook saw `start_session`'s whole input and its result, which is text only (`{ result: [{ type: 'text', text }], text }`). The `session_id` (`local_<uuid>`) is inside that sentence, so adoption reads it with a pattern; a reworded answer leaves the row handed off, and `status` says the id was not found. `get_session` on the child showed `claude-sonnet-5-5` at `medium`, `parentSessionId` the coordinator and `detached: false` (that run had `use_worktree: false`); the child could not tell its own effort, so the requested effort is what is confirmed, by `get_session`, never by the worker. `collect` reads the model and effort out of `get_session`'s answer (matched by pattern, as the session id is) and records them as observed, with a note when they differ from the request; an answer that states neither leaves the row unverified, with a note. The mod's own `$.tool.call` of `get_session` and `list_events` answered as the model's calls did, under bypass permissions. A `start_session` on a notice turn was refused by the app with `isError`. Seen live on 2026-11-08 (`TASK-0201`): two session workers side by side, the next person-started prompt handing off a waiting task, adoption by the mod, `collect` reading each session's report, and each session nested under the coordinator in the sidebar. Not yet seen live: `cancel` on a live session; the mod's reads under auto mode; a proposal card's start.
- **Tokens**: summed from the `usage` each worker's `turn.complete` carries, as agent-watch reads it; seen in the test kit only. Session workers report none to the mod.
- **Audit**: one row a task in `$.store` (ids, role, class, requested and observed settings, status, times, allowed files, report status, hand-off), at most 200, no prompt, no report body, no reasoning. The run mirror (`task-orchestrator:run:<session id>`) is another matter: it holds each task's prompt and report, each report field capped at 2000 characters, since a restore needs them. Only the five report fields are capped; prompts, assignments, notes and reasons are not. It is deleted by `/orchestrate reset` only, not when the session ends.
- **Wake by the end note** (2026-11-05, Claude Code desktop, auto mode): in this session the coordinator was woken by each worker's end note, and one `collect` printed the report. This settles, for subagent workers, the question *Advisory* leaves open: whether `$.session.append` wakes an idle session.
- **A worker's end is not seen inside a `collect`** (2026-11-05, Claude Code desktop 2.1.318, 0.5.5): L5 ended 2.3 s after its spawn; a `collect` started before that waited the full 8.9 s and still answered `running`; L4 the same (ended at 7.1 s, wait 8.8 s). The worker's `turn.complete` reaches the mod only after the coordinator's `tool.call` hook returns, so no subagent task can end inside the wait: the wait catches only a session read through the app. The end note then wakes the coordinator and one `collect` prints the report. The builder saw the same in the test mock (a `turn.complete` from the test body during a wait was invisible; one from inside the `clock.sleep` handler was). Seen three times live; the engine's hook ordering is the likely cause, not confirmed from its source. Since 0.5.6 `collect` no longer sleeps on a subagent task at all (*Enforced in code*); whether a `collect` on a running subagent now answers in well under a second live has not been seen.
- **A forced reload empties `$.state`** (2026-11-06, Claude Code desktop 2.1.318, auto mode, 0.5.6): after `/reload-plugins --force`, run to pick up an edited mod mid-run, `status` printed `No task in the ledger` and agent-watch's panel restarted at B01/S01, while the app's own Background tasks pane still listed all eleven tasks. A plain `/reload-plugins` keeps `$.state` by the engine's types and docs; the docs say `--force` only applies a reload the prompt-cache guard refused (one that adds or removes a plugin MCP server, which this mod's tools are) and say nothing of state. The likely cause, not confirmed from the engine's source: the forced reload replaces the plugin instance and the host's values with it. Since 0.5.7 the run is mirrored into the store and restored at `session.start` (*Enforced in code*); whether the restored run survives a live forced reload has not been seen.
- **Hooks that run beside each other** (0.5.8, from the 0.5.7 review): whether the engine runs two `tool.call` hooks, or a `tool.call` and a `turn.complete`, concurrently is not confirmed from its source; the test kit does interleave them at their awaits (two dispatches in one `Promise.all` both landed only once the ledger writes moved inside the updater). The race-free writes cost nothing when the hooks are serial. Patches whose content is built from a row read before an await (a `notes` append, a token sum, the note-building patches after a post-spawn stop and after a refused resume) still carry that older content; the write itself lands over the current rows (recorded in TASK-0239, not fixed).
- **The turn cap cuts a worker off mid-step** (2026-11-08, Claude Code desktop 2.1.318, 0.5.12): a debugger and a builder at 60 turns each ended with `turn.complete` reason `answer` and no report. Each transcript (`subagents/agent-<id>.jsonl`) ended on a `tool_result`; their edits sat uncommitted in `.claude/worktrees/agent-<id>` on `worktree-agent-<id>` (the agent's meta file names both). Resuming each agent with `SendMessage` finished the work; a re-dispatch would have started a fresh worktree at HEAD. 0.6.0 detects this from the transcript and the worktree (`TASK-0260`).
- **Cap after a dependency ends** (2026-11-05): a queued task waiting on a running dependency is waited on by `collect`, but the cap is not re-checked once that dependency ends, so `collect` may return with the reason "behind the concurrency cap" for it.

## Advisory

- The coordinator protocol (plan, route, dispatch, collect, integrate serially, report with evidence; a model or effort the person names goes on every dispatch, over the table; a reviewer separate from the builder; stop at the limits; the coordinator, not a worker, keeps the person's task board; never commit or push unasked) reaches the model once a session: as the context of `/orchestrate on`, or of the first prompt of a session that starts on (`protocolSent`); `dispatch`'s description only says not to poll. Not polling `collect` is advice too: the end note is what should wake the coordinator, and `$.session.append` woke an idle desktop coordinator on 2026-11-05 (see *Observed, not guaranteed*); other hosts are unseen. A `prompt.compose` section would be the natural place, but the security plugin skips mods' `prompt.compose` hooks, so this mod does not rely on it.
- The delegation contract (objective, inputs, allowed and prohibited files, deliverables, acceptance, tools, requested settings, stop condition, report shape) is text the worker is asked to follow; the fence above is what holds it.
- `Bash` writes by a builder, tester or debugger cannot be checked by path; the one-writer rule and the allowed-files list are what bound them.
- A worker's report is parsed from labelled lines; a worker that gives no `Status:` line is recorded as `partial` with a note to read its report, or, cut off at its turn cap, with the turn-cap reason above.
- The turn reserve (a tenth of the cap, at least two turns, `turnReserve`) is text in the assignment: a worker that ignores it is still cut off at the cap, and `collect` then reports it as above.

## External providers

`providers.ts` declares the adapter interface (`id`, `kind` text-only or agentic, `status`, the variable whose presence says it is configured, the disclosure). The registry holds OpenAI and Grok as `not-implemented`, disabled; `enable` is refused and shows the disclosure. No network code ships in this version: a live adapter would be capability no task here can exercise, and the repository caps such capability (ADR-0039). Native Claude workers need no provider. `ADR-0041` records the decision.
