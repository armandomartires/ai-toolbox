# Developing task-orchestrator

`README.md` is the user-facing spec; `ARCHITECTURE.md` says what is enforced and what is advisory. Rules every mod follows: authoring guide, *Mods*. Loading and testing: runbook, *Loading a mod in development*, and `tests/test-mods.sh --mod task-orchestrator`.

## Modules

The Claude Code plugin is `mods/task-orchestrator/claude/` (`ADR-0054`); the paths below are relative to it, and `README.md` and this file stay one level up.

- `hooks/routing.ts`: data. The task classes, roles and their profiles (description, read-only, max turns, system prompt), the `balanced` table, the policy deltas, the limits, the default config, `familyOf` and `familyRank` (a model's family and its rank on the ladder), `mergeConfig` (an override file laid over a config, refusals named) and `routesUnder` (a policy applied).
- `hooks/router.ts`: pure. `route` (class and the coordinator's overrides → role, model, effort, notes, or `blocked`), `gate` (opt-ins), `fallback` (the next model up the family ladder; none for a model that cannot be placed), `escalate` (one step).
- `hooks/ledger.ts`: pure. The task rows, `isSession` (a `runAs: "session"` task, which holds a slot while handed off and skips the writer checks), `startBlocker` and `runnable` (dependencies, concurrency, writers), `retryTask` (a re-dispatch under a retryable id), `stalledBy` (what a queued task is stuck behind), `isNoVerdict` (auto mode's refusal), `normalizePath`, `resolveIn` and `covers` (the path resolver), `writeBlocker` (the per-call fence), `admit`, `admitNew` and `freeAgentId` (the one admission check into `running`), `stallText`, `blockerFor` and `statusSummary`, `overall`, `line` and `summary`, `auditRow`.
- `hooks/contract.ts`: pure. `buildContract` (the worker's assignment, with its turn cap and the reserve `turnReserve` keeps for the report), `parseReport` (its labelled report), `COORDINATOR_PROTOCOL`.
- `hooks/overrides.ts`, `hooks/providers.ts`: pure. Disclosure of host overrides; the provider adapter interface and its disabled registry.
- `hooks/register.tsx`: the hooks. `session.start` loads the config (defaults ← `~/.claude/task-orchestrator.json` ← `<cwd>/.claude/task-orchestrator.json` ← the store; `loadConfig` reads a `v: 2` store entry and treats an older one as `enabled` only), reads the overrides, registers `/orchestrate`, the four tools and the worker profiles. `command.run` answers `/orchestrate`. `stopWorker` stops an agent with `TaskStop` and returns the refusal, if any, for the note. `agent.spawn` denies a worker's spawn, adopts the coordinator's hand-off of a task auto mode refused, and tracks a worker profile the model took through the Agent tool. `tool.call` answers the mod's tools and fences a worker's calls. `turn.step` records a worker's observed model and effort, and the coordinator's own effort. `turn.complete` closes the task, parses the report, appends a hidden note for the coordinator and starts queued work. A worker with no report whose transcript ends on a tool result stopped at its turn cap: `turnCapReason` names the cap, `workOf` reads its worktree or the session's checkout through `git`, and the task keeps a `stopped at its turn cap` note; that agent's `turn.start` (a resume by `SendMessage`) sets it back to `running`, and its next `turn.complete` closes it (`TASK-0260`); a worker that ended on its own `partial` or `blocked` report is resumable the same way (`isResumable`, `TASK-0289`). For session workers (`ADR-0050`): `prompt.submit` sets `personTurn` from the prompt's origin and hands off a waiting session task, and the coordinator's own `turn.complete` clears it; `tick` takes whether a session task may be handed off now, and only a call inside a person's turn says yes (a worker's end says no); `tool.call` adopts the coordinator's `start_session` (`adoptSession`), and `collect` reads a running session through `get_session` and `list_events` (`refreshSession`).
- `hooks/keep.ts`: `keep($, assignments)` mirrors the ledger, the refused models and each task's assignment into the plugin store under `task-orchestrator:run` with this session's id, only when their JSON changed since the last write; `forget($)` deletes the entry on `/orchestrate reset`; each kept report field is capped at 2000 characters; `restore($, assignments)` fills them back at `session.start` when the ledger is empty and the stored run carries this session's id (`ARCHITECTURE.md`, *Enforced in code* and the 2026-11-06 item). Function declarations, since they take `$` from another file.
- `hooks/view.tsx`: `renderOutput`, `/orchestrate status` and `routing` drawn as SIGMAorbital panels from the data `register.tsx` keeps with `remember` beside the unchanged text; `taskView` (a row and its second line); `statusLineText`; the task-state colours.
- `hooks/sigma.tsx`: the SIGMAorbital design module, a byte-identical copy of `mods/_template/claude/hooks/sigma.tsx` (`ADR-0043`); never edit it here.
- `types/index.d.ts`: the `$.state` contract and the unions the modules import.

## Traps found while building it

- **A hook may not return a deny after `next()` has answered**: the kit reports `returned a deny after its next() was answered`. The `agent.spawn` hook's post-spawn admission therefore stops the agent with `TaskStop` and tells the coordinator by a hidden note instead (`TASK-0265`).
- **`$.fs.read` rejects for a missing file and nothing tells that from another error**: an empty read is treated as missing, a non-empty one that fails `JSON.parse` as malformed and listed under `config refused`.
- **The engine ends a worker at its turn cap with nothing that says so** (2026-11-08, `TASK-0260`): `turn.complete` carries reason `answer` and the last text the worker wrote, as for a real answer. Only its transcript shows it: the last row of `$.session.messages({ agentId })` is a user message with `toolResults`. An agent run in a worktree has it at `<repo>/.claude/worktrees/agent-<agent id>` on branch `worktree-agent-<agent id>`.
- **In `claude plugin test`, nothing beneath the plugins answers `turn.start`, `process.run` or `session.messages`**: a test that sends `$.turn.start` answers it with `on('turn.start', (_, e) => ({ turnId: e.turnId }))`, and stubs git and a transcript with `{ value }` answers (`capWorld` in `register.test.tsx`).

- A `/reload-plugins --force` empties `$.state` (seen live 2026-11-06, `TASK-0238`): `status` said `No task in the ledger` with eleven tasks open. The run is mirrored into the store after every ledger write (`hooks/keep.ts`) and restored at `session.start` under the same session id; the `delivered` set and `protocolSent` are module variables and start over, so after a forced reload `collect` prints each report once more and the next prompt carries the protocol again.
- **A plugin's `$.agent.spawn` reaches the plugin's own `agent.spawn` hook** with `next.origin.plugin` naming the plugin, in the Agent tool's input shape (`subagent_type`, `run_in_background`). The hook passes its own spawns through; the limits were applied by `dispatch` before the spawn.
- **In `claude plugin test`, the engine stub for `agent.spawn` must answer a plugin's spawn with `{ model, agentId, result: { agentId, resolvedModel } }`**: the kit validates the answer as an `AgentSpawnResult` and hands the plugin the record under `result`. `{ model, agentId }` alone reaches the plugin as `{ model }` with no id; `{ result }` alone is "no implementation".
- **A `turn.step` hook is an async generator** (`async function*`, `return yield* next(e)`); a plain function does not type.
- **The test's `session.append` stub must call `next(e)`**: an answer without `next` is refused ("the row is kept").
- **A hook's ten-second budget bills every `$.clock.sleep`**, the one `$` call it does not stop for (`HookBudget`, `$.clock.sleep` in the types). 0.1.0 to 0.4.2 polled with it as if it were free, so a `collect` on a running task overran, its `.catch` passed the call on, and nothing answered ("no tool.call hook answered this call", `B-065`). `collect` now stops at `next.budget.remainingMs` less a margin. In `claude plugin test`, `mock.clock` holds each sleep and lets one go after ten real seconds, so a test of a wait sets its own `timeoutMs` above that, or the kit's five-second limit fails it first.
- **`$.store` is not on the test's `$`**: assert through the mod's own commands, or give `mock.store(on, entries)` its starting rows.
- **Auto mode refuses a plugin's spawn with no verdict** ("the request that produced this action did not ask for one"): its classifier judges an action against the model request behind it, and `$.agent.spawn` can name none. The model's own Agent call passes. In `claude plugin test` a plugin's spawn reaches the engine stub as `subagent_type`, the model's as `subagentType`, which is how `engine({ noVerdict })` refuses only the former.
- `tsc -p mods/task-orchestrator/claude` against the 2.1.312 types reports 31 errors, all in `register.test.tsx`: its command and tool inputs predate fields 2.1.312 requires (`origin`, `presentation`). The tests still run; new calls cast `as never`.
- On 2026-11-05 with TypeScript 6.0.3 and 2.1.318 types, `tsc --noEmit -p claude` reports 142 errors in `register.test.tsx`, one pre-existing in `register.tsx` (`adoptSession` returns `Promise<unknown>` from the tool.call hook) and one in the shared `sigma.tsx` copy; the suite (99 tests since 0.5.8) passes.
