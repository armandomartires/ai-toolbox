# Developing agent-watch

`README.md` is the user-facing spec. Rules every mod follows, and the engine and desktop traps found while building `task-compass`: authoring guide, *Mods*. Loading and testing: runbook, *Loading a mod in development*, and `tests/test-mods.sh --mod agent-watch`.

## Modules

- `hooks/sigma.tsx`: the SIGMAorbital design module, a byte-identical copy of `mods/_template/hooks/sigma.tsx` (`ADR-0043`); never edit it here. Its `IDENTITY`, `agentState`, `fit`, `elapsed`, `kit` and the command-output cache are used below.
- `hooks/sessions.ts`: the session tree (`sessionTree`, `iconOf`, `SESSION_TONES`, `toneToken`, `outcomeOf`, `memberTone`, `memberCaption`, `ledgerBadge`, `progressOf`, `activityLine`), pure, importing only `./sigma` and declaring the row shapes it reads itself. agent-watch's alone: task-compass holds no copy (`ADR-0048`), and gate rule 7 lists only `sigma.tsx`. `SESSION_TONES`, `toneToken`, `memberTone` and `iconOf` survive only for the band's glyphs; the pane colours by state.
- `hooks/model.ts`: pure logic (`mergeListed`, `spawnedRow`; `elapsed` and `fit` re-exported from `sigma.tsx`, everything `sessions.ts` exports re-exported from it), `trimTree` (fits the tree to a line budget, never cutting a head or a ledger task) and `headCaption`, the sessions' tracking (`nextTone`, `assignTones`, `turnEnded`, `turnStarted`, `recordRun`), the task list (`taskChange`, `applyPlan`), the activity (`summarizeCall`, `callStarted`, `callEnded`, `tokensOf`, `turnCounted`) and the alerts (`endedBadly`, `markAlerted`, `alertText`, `runningText`, `watchText`). Tested directly in `model.test.ts`.
- `hooks/sunburst.ts`: pure; `arcs` lays the tree out with equal allocation within each parent, `stateTone`, `stateGlyph`, `stateWord` the one state mapping chart and table share, `rollupOf` the KPI row and SELECTED panel, `sunburstSvg` (desktop `Svg`) and `sunburstCells` (terminal braille `Raster`). Tested in `sunburst.test.ts`.
- `hooks/panel.tsx`: `renderSessions($, e, state, reservedRows)`, the whole Sessions panel (KPI row, chart, legend, SELECTED panel or strip, hierarchy table, the fold), and `sessionsLayout`, the height accounting, which spends `reservedRows` first. It declares the two atoms it owns, `selected` (a press on a row) and `listCollapsed` (the fold; hotkey `s` in a terminal only). Tested in `panel.test.tsx`.
- `hooks/view.tsx`: `renderPane`, the Agents pane (the panel and nothing else, 0 reserved rows); `contributeSessions`, the meter and the panel added to Compass's pane (below); and `renderOutput`, `/agent-watch`'s `CommandOutput` row as a panel.
- `hooks/names.ts`: `PANE` and `TITLE`, the Agents pane's id and title, apart so `band.tsx`, which opens the pane, and `register.tsx` share them without a cycle through `view.tsx` (which imports `drawMeter` from `band.tsx`).
- `hooks/band.tsx`: `drawMeter`, the one drawing of the task-list meter and the running agents' glyphs (an `export function` declaration, since `view.tsx` calls it with `$`; `undefined` while there is no task list and nothing runs), and the `AbovePrompt` band (`registerBand`), which is `drawMeter` and passes to the engine while there is nothing to show or a survey holds the band.
- `hooks/register.tsx`: the hooks: the theme (`syncTheme` at the start, `watchTheme`), `/agent-watch` (its result kept by `remember`), a subagent's activity from its loop's `tool.call` (recorded before `next`, counted in a `finally`, so a deny or a throw still clears it) and its tokens and model from its `turn.complete`, `classic.SubagentStop` refreshing at once, the toasts and the status line from `refresh`, every loop's task list from `tool.call` (`taskChange`: the main loop's into `tasks`, a subagent's onto its row), a Workflow call's result naming its run, agent tracking from `agent.spawn` (a Workflow agent opens its run), a subagent's `turn.start` and `turn.complete` (which ends a Workflow agent), each change through `changeAgents` (toasts, then `syncTones`), a one-second tick that re-reads `$.agent.list()` while an agent is active or ended less than a minute ago or the orchestrator holds an open task, else every ten seconds, and a 400 ms tick that moves `frame` only while an agent is `running`, so a still pane is not redrawn. Tested through the engine stub in `register.test.tsx`.
- `types/index.d.ts`: the `$.state` contract (`selected` and `listCollapsed` among it), and the mirror of the part of task-orchestrator's it reads.

## How agents are tracked

`agent.spawn`'s answer opens the row at once, so a spawn shows before the engine lists it. A subagent's own `turn.complete` ends it (`turnEnded`, `B-066`): its loop runs one turn, and the list is late to say it ended, or drops it without saying so, which left a nested Explore child drawn running for minutes (`TASK-0193`'s live check). `isTurnEnded` keeps that end while the list still says active; the list's own end word still wins over the turn's. A new `turn.start` in the loop (a message woke it) runs it again (`turnStarted`). A teammate is left to the list, since its turn ends in `idle`. A row the list stops naming is kept, so a finished agent stays under Completed for the session. `endedAt` is set the first time a row's status leaves the active ones, and never moved. Its calls and tokens stay in its caption once it ended, since its turn's end is the first to report its tokens.

## Sessions and colour

`ADR-0044` has the session model, `ADR-0046` the dashboard and `ADR-0047` who owns it. A sub-session exists once `assignTones` has given it a key in `tones` (`orch`, `run:<id>`, `agent:<id>`); `sessionTree` derives the rest on each draw: a row's owner is the orchestrator if it is a worker (its ledger names the agent, or `spawnedBy` says so), else its nearest session ancestor, else its Workflow run, else this session. A worker never becomes a session; its own steps go in its caption. The pane colours by **state** (`stateTone`), not by session; the tone index survives only for the band's glyphs, whose pulse is the band re-reading `frame` (`iconOf` by parity; a test advances the mock clock by `FRAME_MS`). A function that receives `$` from another file must be a declaration (`function renderOutput($, e)`), not an arrow; `claude plugin validate refuses the module otherwise.

## Contributing to Compass's pane

`contributeSessions` is hooked on `{ component: 'Pane', requestId: COMPASS_PANE }` (`'task-compass'`, pinned by a test) and is the only hook line that names it. It awaits `next(e)`, then draws, in a column: what `next(e)` returned (Compass's board), `drawMeter` (the band's meter, nothing while there is no task list and nothing runs) and `renderSessions(..., 0)`. The board's height is unknown here, so no row is reserved and Compass's pane scrolls. `contributeSessions` is an exported arrow passed by reference to `on(...)`, which is fine; `drawMeter`, which `view.tsx` calls with `$`, must be an `export function` declaration (above). Limits:

- **Load order.** Compass must call `next(e)` and draw the result after its board (task-compass 0.9.0 does, in either order). A Compass that never calls `next(e)` and loads first hides the contribution; a contributor that wraps Compass is drawn whatever Compass does.
- **The bottom of the chain.** The engine's types make core the last hook, and core answers with its own drawing, `{ type: 'engine', ref }`, so that is what `next(e)` resolves to for the innermost hook when no plugin beneath it drew the pane. `isEngineElement` leaves it out: embedded in a tree, the kit drops the whole tree, which is the board vanishing (red-proved in `slot.test.tsx` and `contribution.test.tsx`). The kit's own base (a `<Box/>`, or a throw when no hook is added) is not core's; whether the real engine answers `engine` there is inferred from the types, not seen, and the debug line shows it. Both hooks catch a rejected `next(e)`: here that draws the meter and panel alone, and the catch also hides an error thrown by Compass's own handler when Compass is the inner hook, by design (a thrown hook costs the board).
- **Debug lines** (`$.ui.log(..., { to: 'debug' })`): `agent-watch: next(e) resolved nothing`, `resolved <typeof> (type <x>)` or `rejected: <message>`, written only when it differs from the last (`noteBelow`, a module-level `lastBelow`, which a reload resets), so a live failure is diagnosable and a redraw adds none.

Tested in `contribution.test.tsx` (agent-watch against a Compass stand-in, both load orders, the meter above the panel and absent without a task list); Compass's side is `mods/task-compass/hooks/slot.test.tsx`.

## The orchestrator tie-in

task-orchestrator owns `ledger`, `policy` and `enabled`; agent-watch reads them through atoms of its plugin name and never writes. Its `types/index.d.ts` mirrors that part of the owner's contract, `Orch<Name>` for the owner's `<Name>`, fields copied verbatim; `check-mods.py` rule 8 fails the gate when the two disagree. A test loads task-orchestrator as an inline plugin (`test(name, { plugins }, body)`) that writes its ledger; the kit evaluates an inline register without its closure, so each ledger is a literal inside it.

A ledger task joins its agent row by `agentId`. The ledger's word wins: a worker that answered but reported `blocked` shows `BLOCKED`. A retried task's earlier agent rows stay under the orchestrator, by `spawnedBy`.

## Workflow runs

`agent.spawn` carries `workflow.runId` for an agent a Workflow script starts, and the Workflow tool's result carries `runId` and `workflowName`; either may come first, so `recordRun` opens the run and fills its name. No `$.agent.list()` names a Workflow agent, so its own `turn.complete` ends it, as it ends every subagent (`turnEnded`): `answer` completed, `aborted` stopped, anything else failed. Seen live in the desktop app (`TASK-0193`): both agents of a run ended with it.

In the desktop app a subagent has no TodoWrite, TaskCreate or TaskUpdate, so a subagent becomes a session there only by spawning children; its own `STEPS` bar needs a terminal session, where subagents have TodoWrite.

## The task list

`taskChange` applies every task tool to a loop's list, the main loop's and a subagent's alike; `applyPlan` repeats the desktop app's `update_plan` semantics (`items` replaces, `advance` completes the step in progress and starts the next pending, `done` and `start` are 1-based) and `wrap_up` completes every step; `task-compass` has its own copy for story matching, kept in step by hand since the sandbox cannot share a module between mods. A test's engine stub answers `ui.render` with a marked `Text`, so a band that passes is told apart from one that drew nothing.

## Activity, alerts, the band's buttons

- A subagent's `tool.call` carries `e.agentId`; the main loop's does not. The hook records the activity around `next(e)` for an agent loop and tracks the task list for the main loop only, in that order.
- `classic.SubagentStop` is bypassed where the security plugin `cc-plugin-sec-default` runs above the mod (observed in a desktop session, `TASK-0182`): the engine sends the event on past the hook and says so in the transcript. The toast then comes from the agent's own `turn.complete`, which the mod also hears, or from the one-second tick; the classic hook helps only in a session without that plugin.
- `isAlerted` lives on the row, not in a module variable, so a hot reload does not toast a second time. `refresh` finds the rows that ended badly inside the updater, which `update` may run twice on a version miss, so the ids are collected in a map and toasted after.
- `$.ui.status` is written only when its text changes, from a module-level `lastStatus`, which a reload resets: the next refresh rewrites it.
- `$.ui.view` is allowed only while answering a press, so both the pane's rows and the band's icons call it from `onPress`. The band's buttons carry no `hotkey`: a bare digit in an empty composer presses a band button, which would surprise.
- A test's engine stub hooks `ui.toast`, `ui.status`, `ui.view` and `ui.open` and records what the mod said; `$.classic.SubagentStop(...)` raises the classic event.
