# Developing switchboard

`README.md` is the user-facing spec. Rules every mod follows, and the engine and desktop traps: authoring guide, *Mods*. Loading and testing: runbook, *Loading a mod in development*, and `tests/test-mods.sh --mod switchboard`. Why one mod rather than three, and why no settings answer: `ADR-0042`.

## Modules

The Claude Code plugin is `mods/switchboard/claude/` (`ADR-0054`); the paths below are relative to it, and `README.md` and this file stay one level up.

- `hooks/model.ts`: pure logic: `asNames`, `isOff`, `toggle`, `setOff`, `addSeen`, `refusal`, `pendingNote`, `pluginDirs`, `isProtected`, `isIdName`, `toolHints`, `shownName`, the server names (`serverOfTool`, `serverOfProvider`, `toolSpelling`, `offName`), the skill listing (`listedSkills`, `dropSkills`), the topics (`skillTopic`, `modTopic`, `groupRows`, `groupKey`: a mod's topic is its manifest's `category`, a skill's its plugin prefix, `Other` and `Standalone` last), and the versions (`samePath`, `repoModDir`, `versionRow`, `versionRows`, `versionLine`, `versionProblems`: a repo mod's loaded version against its manifest's, stale or loaded from another folder), and the command (`parseArgs`, `listText`, `listData`, both grouped by topic). Tested in `model.test.ts`.
- `hooks/sigma.tsx`: the SIGMAorbital design module, a byte-identical copy of `mods/_template/claude/hooks/sigma.tsx` (`ADR-0043`); never edit it here.
- `hooks/store.ts`: `loadOff`, `syncOff`, `saveOff`: `$.store` under `off:<project root>` is the truth, mirrored into `$.state` `off` for the pane. A toggle invalidates `prompt.attachment` and `tool.describe`, so the next turn reads it.
- `hooks/kinds/mods.ts` (`plugin.register`), `kinds/skills.ts` (`prompt.attachment` `skill_listing`, `tool.call` on `Skill`, `skill.prompt`), `kinds/connectors.ts` (`tool.describe`, `tool.call`): one hook set per kind, each recording what it sees into `$.state` `seen`.
- `hooks/inventory.ts`: `readManifest` (a folder's `name` and optional `category`, also read by `plugin.register` from the event's `root`) and `modsFromPluginDirs`: the mods `CLAUDE_CODE_PLUGIN_DIRS` names, by each folder's `plugin.json`, only where `hooks/hooks.json` exists, their categories kept in `$.state` `topics`; `refreshVersions`: the session root's `mods/<name>/claude` manifests (`_` folders left out) into `$.state` `manifests` and `checkout`; `refreshInventory`: those, with the folder and version of each mod from the plugin folders into `$.state` `loaded` (the `plugin.register` hook in `kinds/mods.ts` writes the same for a mod it lets load), plus the skills and MCP servers of `$.session.usage({ breakdown: 'summary' })` with up to three tool names per server (`$.state` `hints`), and `$.tool.list()`. Run at `session.start` and on `/switchboard` and `list`.
- `hooks/register.tsx`: wires the kinds, `/switchboard`, the pane, and `refreshInventory`.
- `hooks/view.tsx`: the pane, one bracketed SIGMAorbital panel (`kit().panel` `bracketed`, as Compass's Sprints and Agents' Sessions, `TASK-0257`) opening on a `kit().stats` KPI row (MODS, SKILLS, CONNECTORS, OFF): sections behind a header (`$.state` `open`), Mods and Skills in topic groups each behind its own header with tabular counts and a `rule` (`$.state` `closedGroups`, keyed `<kind>:<topic>`, and `versions` for the Versions section). Every header is `kit().pressable` (the fold glyph in `controlToken()`, the title a Text, a blank Button laid over them on a desktop, `TASK-0241`), its row Box keyed `<press key>-head` since a Text keeps no key. A row per item is drawn by the shared `kit().toggle` (the square switch; the name text-2, text-3 when off; switchboard's own row a disabled one), and a mod's `pendingNote` from `$.state` `refused`. `ROW_BUDGET` pays for toggle rows (`rowCost`), topic headers and the Versions header (`headCost`) and Versions rows (`versionCost`), spent in drawing order (MODS, Versions, Skills, Connectors); what does not fit is named in one caption. The Versions section (`loaded`, `checkout`, `manifests`; drawn only when the checkout has mods) draws each version as `label` and `value`, a `▲` beside an odd row's name; the footer is the legend with `SWITCHBOARD <VERSION>` at its right, and `renderOutput`, `/switchboard list` drawn as a panel per kind from the `listData` the command keeps with `remember`. `types/index.d.ts`: the `$.state` contract.

## Live behaviour (TASK-0185, Claude Code 2.1.310 and 2.1.312)

- **`cc-plugin-sec-default` passes `prompt.attachment` and `settings.read` on past mods** ("bypassed by cc-plugin-sec-default; beneath runs" in the debug log). It loads in the Windows CLI and the desktop app, not in this host's WSL CLI. So the listing trim works in WSL (`skill_listing: switchboard rewrote it`) and not on the desktop, where the `Skill` refusal still holds. It does not bypass `plugin.register`, `tool.call` or `tool.describe`.
- **MCP servers start connecting before any plugin loads**, so no hook of a mod keeps a server from connecting in the session that loads it. An answer to `settings.read` with `deniedMcpServers` was tried and dropped.
- **`plugin.register` is judged by the plugins admitted before the one loading.** A `--plugin-dir` mod loads first, so it judges the `CLAUDE_CODE_PLUGIN_DIRS` mods after it; the built-in and managed plugins load before it and are never refused.

## Traps

- **The mod inventory is not `enabledPlugins`.** `plugin.register` fires once per hooks module, so a plugin without one (most marketplace plugins ship only skills or servers) is never judged: a toggle for it would do nothing. A mod that loads before switchboard is judged before switchboard's hook exists, so the pane finds it by reading `CLAUDE_CODE_PLUGIN_DIRS` (`TASK-0186`).
- **Only tier `user` is judged.** A managed plugin is the administrator's.
- **No pressable SVG switch exists** (`TASK-0187`). Only a `Button` takes a press (`onPress`), a `Button` holds only strings and `Text` (`<Button> holds strings and Text, not <Svg>`), and a `Client`'s elements are the terminal's, with no `Svg`. The switch is the shared `toggle`: a `plain` Button whose square track is drawn in glyphs.
- **The skill inventory is the context breakdown, not the listing.** `cc-plugin-sec-default` sends `prompt.attachment` on past mods, so on the desktop the listing hook never saw a skill. `$.session.usage({ breakdown: 'summary' })` counts locally and sends nothing.
- **`ccd_*` servers are the desktop app's own** (`ccd_turn`, `ccd_session`, ...). `isProtected` keeps them out of the list and the store's effect: a stored `ccd_` entry is never off.
- **Desktop connectors are named by an id** (`1a59c906-…`) in tool names and the breakdown alike; `shownName` adds the server's first tool names.
- **`$` crosses a file only into a function declaration.** `claude plugin validate` refuses `$` passed to an imported arrow function (`const loadOff = async ($) => ...`); `store.ts` uses `export async function`.
- **The test kit's `$` has no `plugin` or `settings` noun**, so `plugin.register` is not raised in a test: its rule is the pure `refusal`.
- **A skill listing entry is `- <name>: <description>`**, its description possibly running over unindented lines up to the next entry; a plugin's skill is named `plugin:skill`, so a name ends at the first colon followed by a space.
- **A server has two spellings**: `claude.ai Gmail` in `/mcp` and `tool.describe`'s provider (`mcp:claude.ai Gmail`), `claude_ai_Gmail` in its tools' names. `isOff` compares the tool-name spelling; `offName` gives back the one it was turned off by.
- **Gating hooks have no `.catch`** on purpose: a judge that fails lets the call or plugin through, the safe way for a convenience switch to fail.
- **Headless checks**: `claude -p "/switchboard ..." --plugin-dir mods/switchboard/claude --output-format stream-json --verbose` runs the command with no model call; its `system/init` line lists the servers, plugins and skills, and `--debug-file` shows each hook's verdict.

## The tree's bounds (TASK-0256)

The engine draws a tree within its bounds (100,000 characters serialized; the kit cuts a Pane's text at 100,000 and reports `characters of text are drawn up to the first 100000`), and a desktop refuses one past them: it keeps its last drawing, and a fresh mount has none ("switchboard has not drawn in this pane"). A desktop toggle row is about 1,370 characters (Svg track, words, overlay Button), so `view.tsx` spends `ROW_BUDGET` on rows by `rowCost` in document order and draws `+ N more not drawn` for the rest. The kit does not refuse a large hooks tree, so `register.test.tsx` asserts `JSON.stringify(await ui.drawn()).length` against 100,000 with 128 skills and 25 connectors open, on a fresh mount, and with 728 long-named skills.

## The resize handle

The pane's one panel is `kit().panel` with `resize: { key: 'switchboard-handle', rows, held, min: 4 }` (`ADR-0053`). It is not bracketed, so the shared panel draws the handle in a row under it, a plain edge. `rows` is counted as `section`, `group` and `row` draw (a wrapped caption or row is not counted). `sizePanels` is `resizeAnswer` into `panelRows`. `hooks/handle.tsx` is a byte-identical copy of the template's, which `sigma.tsx` imports. Tested in `register.test.tsx`.

## Versions

`VERSION` in `hooks/view.tsx`, `claude/.claude-plugin/plugin.json` and the README move together (`mod-dev` stage 8). The Versions section compares `$.state` `loaded` (`plugin.register`'s `root` and `version`, and the plugin folders' manifests for a mod that loaded before this one; a mod switchboard refused is not loaded) with `manifests` (the session root's `mods/<name>/claude/.claude-plugin/plugin.json`). A mod is *elsewhere* when its loaded `root` is not `<root>/mods/<name>/claude` (`samePath`: separators and a drive letter's case ignored), *stale* when its loaded version differs from the manifest's. The root is the session's project root only, so a session opened in a subfolder of the checkout shows no section. `plugin.register` cannot be raised in a test (no `plugin` noun), so `register.test.tsx` seeds `loaded` through the plugin folders (`/mods`) and the checkout at `/p`.
